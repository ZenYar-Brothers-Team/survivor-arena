# DECISION-0141 — Инфраструктура локализации и состав языков

Status: Proposed

Date: 2026-10-02

Related IP: [IP-35](../implementation/modules/IP-35-localization.md), IP-26, IP-00, IP-25

Related content IDs: все player-facing имена и описания (SKILL, PASSIVE, SET, CHAR, ENEMY, BOSS, FIELD, TRAVELER, PICKUP, META)

## Context

[GI-11](../playtests/OPEN_ISSUES.md#gi-11--локализация-на-разные-языки) открыт 2026-09-30 без
языков и порядка. Состояние на 2026-10-02:

- около 570 русских строковых литералов в ~80 C# файлах (`GameplayUiCopy` 64,
  `UiToolkitGameplayView` 28, `MetaShopProjection` 25 …) и русский текст в 5 UXML;
- 236 русских `displayName`/`description` в generated content JSON, имена улучшений в
  ручном `MetaEconomy.json`;
- тексты эффектов SET-001…020 живут в `switch` `GameplayUiCopy.SetEffect`, а не в данных;
- склонение «монета/монеты/монет» реализовано вручную только для русского (`CoinText`);
- DECISION-0107 уже назвал `NotificationCopy` местом будущей локализации, UI/UX §18 —
  «Language — только когда реально появляется localization».

Входные данные пользователя 2026-10-02: основной язык — английский; переводы на прочие
языки делает AI; консоли не планируются (Steam PC).

## Decision (предлагается)

### 1. Языки и волны

Доли Steam 2026: английский ~36–39%, китайский упрощённый ~24–27% (сезонно до 50%+),
русский ~9%, испанский ~5%, португальский (Бразилия) ~4–4.5%, немецкий/японский/французский
~2–3%, корейский/польский/турецкий ~1–1.5%.

| Волна | Языки | Условие |
|---|---|---|
| 0 — инфраструктура | `ru` (единственная таблица) | все тексты по ключам, проверки, псевдолокаль |
| 1 — к релизу | `en`, `zh-Hans` | `en` вычитывает пользователь; `zh-Hans` — выборочная вычитка носителем до релиза |
| 2 | `pt-BR`, `es`, `de`, `ja`, `ko`, `fr` | после стабилизации текстов; отдельный scope |
| 3 | `pl`, `tr`, `zh-Hant` | по данным вишлистов |
| Не планируется | арабский, иврит (RTL), тайский, индийские письменности | высокая техническая стоимость, малая доля жанра |

- Исходный язык авторинга остаётся русским: канонические документы и Content Design не
  переводятся.
- Английский — основной рынок и fallback-язык.
- Язык при первом запуске: системный, если он поддержан, иначе английский. Выбор игрока
  хранится в настройках.

### 2. Технология — собственные таблицы строк

Рассмотренные варианты:

| | A. Собственные таблицы (предлагается) | B. `com.unity.localization` |
|---|---|---|
| Загрузка | JSON в `Resources`, синхронно, как весь контент | обязательный Addressables: второй конвейер и шаг сборки контента |
| Авторинг | Python-генератор пишет таблицу контента из Content Design; UI-таблица — текстовый JSON | таблицы — Unity-ассеты; генератору нужен CSV/XLIFF-импорт через Editor |
| UI Toolkit | presenter/ViewState получает готовую строку, как сейчас | data binding `LocalizedString` в Unity 6 |
| Plural/формат | свой поднабор: правила CLDR для выбранных языков, именованные параметры | Smart Strings из коробки |
| Псевдолокаль, импорт/экспорт | свой инструмент, около сотни строк Python | встроены |
| Тесты | EditMode без загрузки ассетов | загрузка таблиц асинхронная, тестам нужна инициализация пакета |
| Шрифт для каждого языка | USS-класс языка на корне панели | Asset Table + Addressables |

Предлагается вариант A. Текст почти весь собирается в коде презентеров, а не лежит на
компонентах сцены. Поэтому главное преимущество пакета — автоматическая привязка
компонентов — здесь не работает, а Addressables добавляет новую подсистему.
Из рекомендаций Unity Localization обязательно перенимаются:

- единственный источник текущего языка;
- свой шрифт для каждого языка с иероглифами вместо запасных шрифтов;
- проверка полноты таблиц, где «ничего не проверено» не считается PASS;
- контекст для каждого ключа;
- проверка отсутствующих глифов;
- отчёт обо всех непереведённых местах.

### 3. Правила текста

- **Ключи и ссылки.** Player-facing текст адресуется ключом. Content-тексты используют
  ключи, производные от стабильного ID (`content.SET-001.name`).
- **Ссылки на сущности.** Описание ссылается на имя сущности (`{ref:SKILL-003}`), а не
  содержит его копию. Так один термин не переводится по-разному.
- **Целые шаблоны.** Шаблоны — целые фразы с именованными параметрами. Склейка фраз из
  частей запрещена. Множественное число задаётся категориями CLDR.
- **Метаданные ключа.** Каждый ключ имеет контекст: где показывается и что означает.
  При необходимости задаётся лимит длины.

### 4. AI-перевод

- **Глоссарий.** Перевод идёт с глоссарием терминов.
- **Двойной источник.** Модель получает русский исходник и английскую версию как вторую
  опору.
- **Хэш исходника.** Каждый перевод хранит хэш исходника. Изменённый русский текст
  помечает переводы устаревшими.
- **Проверка до релиза.** Автоматические проверки и ручная вычитка английского и
  китайского выполняются до релиза.

### 5. Settings

В Settings → Other появляется Language. Переключение применяется сразу, без перезапуска,
и сохраняется вместе с остальными настройками.

## Consequences

После approval:

- **UI/UX Design §18 «Other».** Language заменяет оговорку «только когда реально
  появляется localization»; уточнение дописывается в контракт DECISION-0038 (settings file).
- **[UI/UX §14 Notifications](../UI%20%20UX%20Design.md).** `NotificationCopy` переходит на
  ключи без изменения поведения.
- **Game Design и Content Design** не меняются. Русские имена в карточках остаются
  каноническим источником.
- **IP-35** становится исполнимым. IP-26 и последующие UI-изменения обязаны добавлять
  тексты только через ключи.
- **Правила.** `.claude/rules/ui-code.md` получает правило «player-facing литералы только
  в таблицах»; `check_project.py` получает localization checks.
- **Тексты эффектов сетов** (`GameplayUiCopy.SetEffect`) переезжают из кода в таблицу
  контента. Текст не меняется.
- **Telemetry, профиль и сохранения** хранят только ID, не локализованный текст.

## Open questions

   вариантов) или раздельные `es-ES`/`es-419`.
2. Домашний источник текстов эффектов сетов: UI-таблица (предлагается) или карточки
   Content Design (требует отдельного approval правки канона).
3. Локализуется ли DEV drawer. Предлагается: нет, development-поверхности остаются вне
   проверок.
