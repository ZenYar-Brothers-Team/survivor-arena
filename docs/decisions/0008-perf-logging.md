# DECISION-0008 — Пороговое perf-логирование горячих операций

Status: Approved

Date: 2026-09-15

Related IP: IP-04, IP-08; правило применяется ко всем будущим IP

Related content IDs: —

## Context

Ревью PR #6 и последующий разбор кода отметили несколько мест, чья стоимость растёт вместе с числом сущностей в забеге (`EnemyRegistry.TryFindNearest` — линейный перебор врагов на каждый таргетинг-тик; `SceneActiveSkillEffectExecutor.TickMines` — сканирование всех мин против всех врагов, дважды за кадр). При текущем масштабе fixture-контента (один враг, единичные мины) это не проблема, но при сотнях врагов может стать узким местом незаметно, без сигнала до профилирования вручную. Пользователь запросил универсальный механизм: логировать длительность операции только при превышении критического порога, чтобы не создавать нагрузку и не спамить лог в штатном режиме.

## Decision

- Новый модуль `Game.Diagnostics` с `PerfGuard` (`readonly struct IDisposable`, без аллокаций) и `PerfLog` (throttling + сам `Debug.LogWarning`).
- Использование: `using (PerfGuard.Measure("Descriptive.OperationName", warningMilliseconds))`. Лог печатается только если операция превысила порог, и не чаще одного раза в 2 секунды на одно имя операции — постоянно медленный путь не заваливает консоль.
- Единственный уровень — `Warning`; критичность видна по самому факту появления лога и величине превышения в тексте сообщения, отдельный уровень `Critical` не заводился.
- Подключено к `EnemyRegistry.TryFindNearest` и `SceneActiveSkillEffectExecutor.TickMines` как первые кандидаты.
- Правило для будущего кода записано в `AGENTS.md` (раздел «Coding conventions»), чтобы оба агента (Claude Code и Codex, оба читающие `AGENTS.md`) применяли его последовательно.

## Consequences

- Game Design и Content Design не затронуты — чисто инфраструктурное изменение.
- `Game.Diagnostics` — независимый модуль без игровых зависимостей, подключается из любого модуля без риска циклов.
- Новые горячие точки (например, `GameplayUiPresenter.RefreshAll`, отмеченный в ревью как потенциально частый rebuild) не инструментированы в этом решении — это открытый пункт для последующей работы, не блокирующий текущий scope.

## Approval

Пользователь явно утвердил 2026-09-15: «нужно добавить в правила ИИ для чего генерить логи... вывод лога происходит только если преодолевается критическое значение... такой логгер нужно добавить как-то универсально» и выбрал «Один порог, всегда Warning» при уточнении.
