# DECISION-0051 — Первая карта только с исходно открытым контентом

Дата: 2026-09-22.
Статус: Approved — пользователь утвердил DECISION-0050 и поручил составить план
первой карты только для исходно открытого набора. Реализацию этим запросом не начинать.

## Решение и граница

Подготовлен [вложенный этап FIELD-001](../implementation/milestones/FIELD-001-start.md)
ревизии `field-001-start-R1` внутри общего `design-sync-R2`. Отдельного независимого
плана, реестра статусов или fork игрового дизайна нет. Execution order и packet
статусы хранятся только в [STATUS](../implementation/STATUS.md).

Включены исходные 10 active / 10 passive / 5 sets из DECISION-0050, CHAR-001,
FIELD-001, ENEMY-001…005 и ENEMY-007 (шесть ordinary типов по последующей
поправке [DECISION-0052](0052-field001-six-ordinary-enemies.md)),
BOSS-001, MIDBOSS-001, TRAVELER-001/002/005, XP, PICKUP-001 и Книга.
Остальные playable/build IDs не реализуются ради этого этапа. Для mid-boss
предусмотрена встреча в FIELD-001 schedule; точный момент остаётся в data packet.

После победы разрешены запись результатов, валюты, прохождения и утверждённых
unlock metadata. Реализация боевого контента, других полей и персонажей,
открывающихся позднее, сюда не входит. Их определения нельзя заменить fixtures
ради запуска повторного забега. Игровая проверка повторного FIELD-001 с расширенным
профилем остаётся в полном плане; ограничивать игрока начальным пулом навсегда нельзя.

Набор 10/10/5 проверяется на отдельном новом профиле, без удаления пользовательских
сохранений. Настоящий production прогресс сохраняет глобальные unlocks по DECISION-0050.
Для повторения стартовой приёмки используется новый отдельный профиль или test harness.

## Packet dependencies

Каталоги поставляются точными поднаборами. Потребителю первой карты достаточно
проверенного требуемого packet, а не окончания всех десяти карт/двадцати врагов.
Это уточняет WORKFLOW §4: каждый packet имеет own acceptance, current revision
и evidence в STATUS. Незавершённый остаток того же IP не блокирует независимый
поднабор; общий контракт/API, от которого он реально зависит, всё ещё обязателен.
Полный IP не получает Implemented/Verified по одному поднабору.

Порядок этапа регистрируется в STATUS; F1-00 — подготовка полных данных и gates.
Это Ready к подготовке спецификаций, а не к production-реализации неполных карточек.
Более поздние численные конфликты SET-002/015 остаются в полном backlog и не
блокируют пять стартовых сетов, если не обнаружится общий контрактный конфликт.

## Последствия и проверка

IP-25/26 получают новые target criteria после изменения unlock mapping/UI;
их прежнее Verified подтверждает только предыдущую версию. Foundation contracts
без изменения поведения сохраняют свои проверки. Approved art переиспользуется
по manifest, но fixture binding не считается production definition.

Доведение первой карты не закрывает полный IP-27, каталоги или поздние unlock
игровые сценарии. Runtime в этом изменении не меняется. Проверка плана — точность
ID/состава, отсутствие циклов packet dependencies, ссылки, полнота remaining scope
и сохранность единственного execution registry.
