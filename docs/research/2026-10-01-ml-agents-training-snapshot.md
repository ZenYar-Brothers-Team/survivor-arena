# Снимок исследования обучения бота через Unity ML-Agents

Дата снимка: 1 октября 2026 года. Документ описывает уже выполненные эксперименты и измеренные результаты. Он не задаёт дальнейший план и не утверждает, что выбранный метод оптимален.

## Контекст и доступность материалов

Исследование проводилось для Survivor Arena, поле `FIELD-001`, в отдельном локальном рабочем дереве `survivor-arena-ml-agents`. Оно было создано от `develop-evg` на коммите `3d5f2206fee1284aff72a8aa8654cb1aa112e07d` и к моменту снимка оставалось на detached HEAD с незакоммиченными изменениями ML-01. Обычная игра и её выбранная политика управления не заменялись исследовательской моделью.

Этот Markdown-файл можно перенести отдельно. Он **не содержит** исходный код экспериментальных добавлений, исполняемые Unity-сборки, PyTorch checkpoints, ONNX-файлы и отчёты отдельных эпизодов. Код ML-01 на дату снимка находился только в локальном экспериментальном worktree; `TestResults/` и виртуальное окружение `.venv/` игнорировались Git. Приведённые ниже относительные пути указывают, где эти материалы лежали в том worktree, и служат описанием эксперимента, а не обещанием их наличия в ветках `develop` или `develop-evg`.

Договорённости проекта: `docs/Game_design.md` задаёт правила игры, `docs/implementation/STATUS.md` — статус работ, `docs/implementation/modules/ML-01-unity-mlagents-training.md` в экспериментальном worktree — исследовательский контракт. Показатели микросцены не являются результатами полной игры.

## Техническая среда и интеграция

| Компонент | Использованное состояние |
| --- | --- |
| Unity | 6000.6.0f1, Windows standalone development player |
| Unity package | `com.unity.ml-agents` 4.0.0, локально встроенный в `Packages/com.unity.ml-agents/`; имелся compatibility fix для устаревшего `GetInstanceID()` в Match3-интеграции Unity 6.6 |
| Python | `mlagents==1.1.0`, `torch==2.2.2` CPU, `setuptools==80.9.0`; версии записаны в `scripts/ml_agents/requirements.txt` экспериментального worktree |
| Алгоритм | PPO из ML-Agents, один Unity environment/worker, сеть из двух скрытых слоёв по 128 узлов, нормализация наблюдений |
| Обмен | Локальный ML-Agents communicator, Python trainer → отдельный Unity player; inference также проводился через Python communicator |

Для настоящего `FIELD-001` был добавлен опциональный `movementPolicy.id = mlAgents`, версия 1, только в отдельном balance automation player. Агент передавал два непрерывных значения направления через `BotDirectionSource` в обычный `PlayerMover`. Игровые атаки, выбор улучшений, враги, награды и завершение забега оставались обычными системами. Решение о движении запрашивалось лишь в состоянии `RunState.Running`; в первом полном опыте интервал составлял 0,2 секунды игрового времени. Естественные Victory/Defeat завершали эпизод, административное прерывание не считалось таким исходом.

Общее наблюдение (`MLObservationEncoder`) имело **32 числа**: доля здоровья, прогресс XP, доля времени забега, нормализованные координаты игрока, видимые количества угроз и XP, признак полноты наблюдения; затем три ближайшие угрозы по пять значений (относительные x/y, скорость x/y, тип) и три ближайших XP по три значения (относительные x/y, ценность). Отсутствующие объекты заполнялись нулями. Действие — две непрерывные координаты направления в `[-1, 1]`; нечисловые значения заменялись нулями.

Исследовательская награда настоящего забега за шаг: `0.0005 × прошедшие активные секунды + 0.02 × вновь собранный начисленный XP − 0.5 × вновь потерянная доля здоровья`; отрицательные приращения этих трёх входов обрезались до нуля. Естественная Victory добавляла `+3`, Defeat — `−1`. Это выбранный для опыта сигнал, а не измеренная цель человека или правило игрового баланса.

Основные экспериментальные файлы: `Assets/Game/Bootstrap/Automation/MLTrainingAgent.cs`, `MLObservationEncoder.cs`, `MLTrainingReward.cs`, `MLMicroArenaAgent.cs`, `MLMicroArenaConfig.cs`, `MLMicroArenaBootstrap.cs`, `Assets/Game/Bootstrap/Editor/MLMicroArenaBuild.cs`, `Assets/Scenes/MLMicroArena.unity`; Python-запускатели — `scripts/ml_agents/train.py`, `build_micro.py`, `micro_run.py`. Связка с настоящим забегом проходила через `Assets/Game/Bootstrap/Automation/AutomationRunHost.cs` и `Assets/Game/Automation/ExperimentConfigLoader.cs`. Эти изменения не включены в данный Markdown-коммит.

## Первый опыт в настоящем FIELD-001

Первый отдельный player находился в `TestResults/ml-agents-build/agent.exe`. Конфигурация обучения `scripts/ml_agents/field001-training-002.json` задавала свежий профиль, `FIELD-001`, `CHAR-001`, `mlAgents/v1`, один chain, максимум 200 забегов, скорость симуляции 5. Конфигурация PPO (`scripts/ml_agents/ppo.yaml`) имела batch 128, buffer 2048, learning rate 0.0003, gamma 0.99, horizon 128, максимум 5000 шагов. Первоначальная 20-забеговая проверка связи экспорт модели не дала из-за несовместимой версии PyTorch; затем была закреплена версия 2.2.2.

Второй запуск дошёл до 5056 шагов и экспортировал модель (`TestResults/ml-agents-field001-trial-002`). Было 39 естественных поражений и одно административно прерванное прохождение, без побед. Естественные забеги: среднее время 31,51 игровой секунды, средний собранный начисленный XP 2,28. На пяти новых забегах Python inference того же checkpoint дал пять поражений, среднее время 29,03 секунды и XP 2,40. SHA-256 ONNX: `7415c810ee2bd49ab2eb63a370b6961f5c0f653a489aa1928621ad7f72875471`.

Контроль `safePickup/v1` на той же сборке дал три естественных поражения с длительностями 95,24 / 622,61 / 515,03 секунды и собранным XP 6 / 16 / 34. Четвёртый контрольный забег был прерван; набор мал и использовал другие seeds. Данные первого опыта **не показали улучшения настоящего FIELD-001** обученной моделью. ONNX не встраивался в обычную сборку игры.

## Почему появилась отдельная микросцена

После неудачного полного опыта была создана короткая диагностическая сцена `MLMicroArena`: один игрок, один XP pickup, необязательная круговая угроза, короткий лимит времени. Она использовала тот же кодировщик 32 наблюдений и расчёт скорости движения, но упрощала игровую задачу. Исходы `collected`, `collision`, `timeout` записывались по эпизодам в `episodes.jsonl`. Это проверка способности учить движение и обход, а не эквивалент полного забега.

Физический шаг был 0,02 секунды, решение агента — каждые пять шагов (0,1 секунды) с удержанием действия между решениями, скорость игрока 4 единицы/секунду. Радиусы игрока/угрозы/XP: 0,30 / 0,55 / 0,45. Игрок и XP создавались слева и справа от угрозы на x=0; y и, в поздних опытах, x варьировались детерминированным `System.Random(seed + номер эпизода − 1)`. Начальные x-зазоры проверялись так, чтобы игрок не появлялся в радиусе угрозы и XP не перекрывался с ней. Все координаты ограничивались квадратной ареной с полуразмером 6.

Награда микросцены за физический шаг: `−0.001 + 0.3 × (предыдущее расстояние до XP − текущее расстояние)`. Завершение добавляло `+5` за XP, `−3` за столкновение, `−2` за истечение времени. Условия терминального события проверялись в таком порядке: сбор XP, столкновение, таймаут. Параметры задавались отдельными JSON, это не баланс FIELD-001.

Для 60-тысячешаговых стадий `micro-ppo-shaped.yaml` задавал PPO: batch 128, buffer 1024, learning rate 0.0003 с линейным расписанием, beta 0.005, epsilon 0.2, lambda 0.95, три эпохи, gamma 0.99, сеть 128×2, нормализация, horizon 64, summary каждые 3000 шагов. `warm-start` копировал предшествующий checkpoint и начинал новый счётчик шагов с нуля. Исторический первый basic-опыт записан как 60 000 шагов; текущая локальная версия `micro-ppo.yaml` позднее имела `max_steps: 30000`, поэтому она сама по себе не восстанавливает исторические параметры первого запуска.

Запускатели проверяли входной JSON, геометрию, существование модели и SHA-256 player executable/Data по `build-manifest.json`, создавали новый каталог результата и записывали `experiment.json` с входами и происхождением checkpoint. `--allow-build-mismatch` использовался явно при переносе checkpoint между исследовательскими сборками с теми же 32 наблюдениями и двумя действиями; оба манифеста оставались в experiment marker. Трасса `--trace` писала положение и команду каждого физического шага. Python inference иногда сообщал об исчерпании перезапусков worker после намеренного выхода player; запускатель признавал прогон завершённым только при наличии всех последовательных отчётов эпизодов.

## Измеренные стадии микросцены

Числа ниже означают `собран XP / столкновение / таймаут`; строки одной пары используют одинаковые диапазоны seeds. Эти результаты относятся только к микросцене.

| Условия и контроль | Измеренный результат |
| --- | --- |
| Без угрозы, 100 новых эпизодов | случайное движение 27 сборов; прямое движение к XP 100; PPO после 60 000 шагов 100 |
| Первая постановка угрозы, x игрока −0,75 / угрозы 0 / XP +0,75 | геометрия была ошибочной: 29 из 100 стартов уже пересекали радиус угрозы; полученные 52/100 PPO против 41/100 прямого движения не служат измерением обхода |
| Исправленная короткая дистанция, x −1,5 / 0 / +1,5, seeds 100000–100099 и 200000–200099 | прямое движение 42/58/0 и 44/56/0; первая стадия PPO 64/36/0 и 66/34/0; вторая стадия PPO 78/22/0 и 77/23/0. Каждая стадия — 60 000 шагов |
| Более длинный маршрут, x −2,5 / 0 / +2,5, 2,5 секунды, два набора по 100 | прежняя модель 67 и 71 сбор; дополнительная 60-тысячешаговая стадия 90 и 92. На коротком маршруте та же модель снизилась до 55 и 59 сборов |
| Смешанная дистанция: центры −2/+2, jitter ±0,5, два набора по 200 | предыдущая длинномаршрутная модель 153/21/26 и 143/35/22; дополнительная 60-тысячешаговая стадия 178/20/2 и 175/25/0. На коротких наборах 77 и 80 сборов, на длинных 87 и 90 |

Трассы показали, что многие неудачи исправленной короткой постановки происходили в первые 0,30 секунды ещё до x=0. Дополнительный горизонтальный зазор между стартом и суммой радиусов был 0,65 единицы, что при скорости 4 соответствует 0,1625 секунды; интервал решения — 0,1 секунды. Проверка сохранённой модели с решением каждый физический шаг без переобучения дала 78/100 и не изменила агрегированный результат. Повторный inference одного checkpoint иногда менял исход отдельных эпизодов при тех же seeds, поэтому различия в несколько эпизодов не считались устойчивым эффектом.

## Последняя измеренная стадия: движущаяся угроза

В новой микросцене y угрозы менялся по `baseY + A × sin(phase + 2πft)`, вертикальная скорость — `2πfA × cos(phase + 2πft)`, где время `t` — игровые секунды, `phase` заново выбиралась из `[0, 2π)` для каждого seed. При `A=0` старая постановка оставалась неподвижной. В испытании использовались `A=0,75`, `f=0,75 Гц`, максимальная скорость угрозы около 3,53 единицы/секунду. Её текущие положение и скорость передавались в уже существующих слотах наблюдения. Микросцена сохраняла смешанную начальную и целевую дистанцию.

Сборка v8 на Unity 6000.6.0f1 успешно завершилась после четырёх прежних native crash попыток v7; в последнем crash log была ошибка недостаточных ресурсов памяти. SHA-256 Data новой сборки: `72f2cc4fe303b6e77319236a383dc1a9f50da4a67f387191428def13aebb054d`. Модель была warm-start от смешаннодистанционной и обучалась ещё 60 000 шагов, завершив 5448 эпизодов. ONNX SHA-256: `b960c223897491e7faf332421bd7b79142f7e64a7600fdbb484769ff95cb0274`.

| Условия (эпизодов) | Прежний checkpoint | Новый checkpoint | Прямое движение |
| --- | ---: | ---: | ---: |
| Движущаяся угроза, seeds 700000–700199 (200) | 132 / 60 / 8 | 167 / 33 / 0 | 78 / 122 / 0 |
| Движущаяся угроза, seeds 800000–800199 (200) | 119 / 69 / 12 | 157 / 43 / 0 | не запускалось |
| Неподвижная короткая, seeds 100000–100099 (100) | 83 / 17 / 0 | 82 / 18 / 0 | не запускалось |
| Неподвижная длинная, seeds 300000–300099 (100) | 94 / 5 / 1 | 88 / 5 / 7 | не запускалось |

В двух новых наборах с движущейся угрозой прирост составил 35 и 38 сборов из 200. На коротком прежнем маршруте измерение почти не изменилось; на длинном число сборов снизилось на шесть, а таймаутов выросло на шесть. Это сравнение сделано на одном player build и совпадающих seeds внутри каждой строки, но Python inference ранее показывал неполную повторяемость отдельных исходов. Из этого не следует эффект в FIELD-001.

## Проверки и границы выводов

- Настоящий player и микросцена подключались к Python trainer, принимали 32 наблюдения и два действия, создавали терминальные отчёты и ONNX. Для движущейся угрозы все перечисленные evaluation-прогоны выдали ожидаемое число последовательных эпизодов; запускатель не нашёл терминальных исходов быстрее физически возможной нижней границы. В первом новом 200-эпизодном прогоне 190 конечных положений угрозы отличались от начальных более чем на 0,01 единицы.
- Выбранные EditMode-тесты награды и конфигурации выполнились: **15/15 Game.* passed, 0 failed/skipped**. Проверяющий `scripts/check_project.py` не выдал общий reusable `PASS`, поскольку Unity во время проверки изменила `ProjectSettings/ProjectSettings.asset` и `ProjectSettings/Packages/com.unity.learn.iet-framework/Settings.json`. Полного EditMode/PlayMode smoke для ML-01 не было.
- Сохранённые микромодели оценивались через Python inference; ONNX не внедрялся в обычную игру. Для полного FIELD-001 зафиксирован неуспешный ранний опыт. Побед или измеренного улучшения полного забега новым микрочекпоинтом на дату снимка нет.
- Код, версии и пути этого снимка относятся к незакоммиченному локальному эксперименту. Коммит только этого Markdown-файла не делает исследовательскую реализацию или веса моделей доступными на другой машине.
