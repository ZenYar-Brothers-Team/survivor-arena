## Предлагаемая композиция

### Граница макета и чистовой темы

Прежний план IP-26: сначала композиция, затем тема каждого среза. В HTML уже
применены palette/type/основные состояния, но это не финальная отделка кнопок.
Art Direction §12.2 предусматривает матовые кожаные/пергаментные поверхности,
2 px контур, слабый внутренний блик или фактуру до 3–4%, умеренные угловые маркеры
и явные hover/focus/pressed/selected/disabled. Тяжёлые резные/металлические рамки,
глянец и сильный bevel не планировались. Вопрос пользователя о слишком серых
поверхностях не трактуется как approval нового стиля или поручение перекрасить
все экраны сейчас. Тематический проход остаётся отдельным шагом после layout.

### Главное меню

Слева спокойная тёмная зона примерно на 40% экрана: название игры и одна колонка
действий. «Играть» — единственный тёплый primary; ниже «Развитие», «Настройки»;
«Выйти» ниже с меньшим акцентом. Не добавляем новости, счётчики, описания лора,
новую валюту или кнопки.

Это знакомый экран входа, а не ещё одна карточная сетка. Фон декоративный,
не живой gameplay и не selectable field. По замечанию пользователя о несходстве
гоблина и фона добавлены варианты, не меняющие действия и расположение меню:

- A — исходная композиция: существующая thumbnail окраины и отдельный Клёпка;
  сохранена по прямой просьбе пользователя.
- B — только существующий пейзаж, без наложенного персонажа.
- C — крупный существующий герой на спокойной плашке, без пейзажа.
- D — по дополнительному запросу пользователя сгенерирована единая иллюстрация
  побега гоблинов от рыцарей. После feedback v003: сосредоточенные гоблины без
  улыбок, синяков и жалобности; исходные рыцари и естественные беговые позы.
  Чайник убран по разрешённому пользователем упрощению: бросок v002 не понравился.
  Слева сохранена тёмная зона под меню, отдельный sprite поверх сцены не выводится.
- E — эксперимент объёма на основе D v003: восстановленный фон с рыцарями и
  отдельный прозрачный слой гоблинов; справа Шепотка — в текущем v002 взрослее,
  со свёрнутыми картами вместо сумки, только для этой иллюстрации
  ([edit packet](ui-entry-r1/menu-shepotka-review.md)). Слои плавно смещаются/слегка поворачиваются
  с разной амплитудой, в том числе от указателя. Три выраженных широких луча за
  гоблинами и 18 средних полупрозрачных пылинок перед обоими героями постоянно
  движутся без мыши; размах движения лучей увеличен без изменения яркости,
  общей подсветки персонажей нет.
  Это не полный 3D и не цикл бега. [Layer brief и prompts](ui-entry-r1/menu-depth-review.md).

D пока только preview: [brief, prompts и provenance](ui-entry-r1/menu-art-review.md).
Пользователь положительно оценил направление v001 и уточнил настроение после v002;
В итоговом review выбран E с Шепоткой v002, не цельный D v003. Production PNG,
GUID и каталоги этим approval не меняются. Старые thumbnails, v001/v002/v003
и вариант D сохранены как предыдущие варианты.

#### Лёгкое движение иллюстрации — browser proposal

По запросу пользователя D получил мягкое приближение/смещение цельного PNG и
несколько слабых пылинок справа. Transform не применяется к меню; лица, руки и
ноги не деформируются. Это «живая иллюстрация», не видеоролик или цикл бега.
Scale 1.025–1.045, translation X −0.25…0.4% / Y −0.2…0.2%, 24 s alternate;
семь частиц размером 5 px с max opacity 0.2, только в правых 55% кадра. Значения
пробные для review, не production content. A/B/C сохраняются неподвижными.

Переключатель находится вне игрового viewport; reduced-motion принудительно
отключает эффект, скрытая вкладка останавливает время, уход с экрана удаляет
декор. UI intents/access не меняются. PNG v003 и approval gate неизменны.
Если эффект будет выбран для Unity, потребуется отдельная реализация и runtime
проверка lifecycle; CSS keyframes не являются USS и не переносятся буквально.

E сохраняет те же motion toggle/reduced-motion/visibility/cleanup границы.
Передний слой имеет настоящую alpha; это AI-подготовленная версия, не обещание
пиксельной идентичности исходному изображению. Размещение скорректировано только
CSS transform/размерами, исходные PNG не перезаписаны. Pointer response сглаживается
одним временным requestAnimationFrame-loop; при остановке/уходе/скрытии он отменяется.
Декор не ловит input и не двигает кнопки. Детали и проверка — в layer brief.

### Выбор персонажа

Три зрительные зоны, без трёх одинаковых рамок:

```text
Выбери персонажа                                  1 · Персонаж — 2 · Поле

Сетка героев       Крупное изображение             Имя и одна строка роли
2 колонки         существующего body              Стартовое умение + иконка
с прокруткой                                      2 строки специализации
                  Условие открытия,               Только выбранные автором
                  если герой закрыт               отличия от baseline

Назад             текущий выбор                               Выбрать поле →
```

Слева около 30% ширины; справа единая панель изображения и информации. В карточке
roster только body, имя и короткое состояние. Большое изображение не зажимается
в маленький круг. Новые portraits не производятся.

По DECISION-0087 неполученный body в обеих зонах — только чёрный силуэт, без
внешних деталей. Выполненное условие до покупки тоже не раскрывает изображение;
после получения показан исходный цветной sprite. В HTML это render-only filter,
не отдельный raster asset. Имя, умение и lock reason остаются.

Клик/Enter/Space закрепляет просмотр, не переходит дальше. Отдельная фиксированная
кнопка «Выбрать поле» подтверждает доступного персонажа. Hover не меняет выбор.
Предлагается разрешить read-only просмотр закрытого героя, но не selection/run:
условие рядом с крупным изображением видно без скролла, confirm выключен.
Это уточнение inspection UX требует approval вместе с композицией; owner доступа
остаётся CharacterSelectionSession, UI не подменяет его SelectedId закрытым ID.

На Клёпке: короткая роль, Бросок камня, специализация +60% урона камня и +25%
скорости использования. Не заполняем пустой authored highlights list нейтральными
100% или выдуманными бонусами. На Бугре показываем вариант трёх highlights по
approved CD: здоровье +20%, движение −8%, урон умений +5%; выбор этих полей для
будущего presentation metadata — часть предложения, не скрытая запись в JSON.
Специализация клинков отдельно: +60% damage, +25% size. Базовый damage не выводим.

Постоянные улучшения профиля, если есть, сохраняются компактным отдельным блоком
по существующему источнику; не смешиваются с особенностями героя. HTML использует
пример без permanent upgrades, а не имитирует весь профиль. Точные draft weights
и полный внутренний stat table не нужны на основном экране.

### Выбор поля

```text
Выбери поле                                      1 · Персонаж — 2 · Поле

Пять карточек: thumbnail / название / сложность / доступ
Пять карточек: thumbnail / название / сложность / доступ

Выбранное поле              Короткая причина блокировки (если есть)

Назад                        выбранный персонаж                    Начать забег
```

Утверждён компактный grid без большой правой панели. Десять карточек помещаются
в 5×2 в обоих разрешениях без scroll; при расширении каталога скроллится только
grid, footer остаётся на месте. Текущий выбор устойчив к hover и прокрутке.
Сложность — прежнее authored значение 1–5, показано число (не только цвет).
Описания окружения полностью убраны из экрана, не спрятаны в tooltip.
Не выводим wave timings, enemy pool, boss stats или постоянный лимит стартовых
умений. Закрытое поле можно осмотреть; кнопка старта выключена, условие понятно.

В footer — герой с маленьким body и именем, чтобы не забыть предыдущий выбор.
Back возвращает к персонажу без сброса допустимого выбора. Start Run повторно
проверяет оба доступа существующим owner; это не быстрый старт по клику на поле.

## Размеры, состояния и длинные списки

- 1920×1080: внешние поля 72 px по горизонтали; 1280×720: 36 px. Это размеры
  кандидата, не новый minimum resolution. Меняются отступы/геометрия, не только
  масштаб всего экрана. Main Menu имеет собственную спокойную композицию.
- Footer не прокручивается. Каталог героев имеет один вертикальный scroll; клик по
  нижней карточке не сбрасывает scroll. Длинная правая character-copy может иметь
  отдельный scroll как запас для будущих описаний/permanent summary; изображение,
  условие lock и confirm остаются видимыми. Текущие обычные примеры помещаются.
- Normal/hover/pressed/selected/focus/locked/disabled различаются. Selected —
  тонкая золотая граница; keyboard focus — явная внешняя рамка. Никаких oval pills
  для категорий. Locked hero — силуэт, locked field — приглушённая thumbnail;
  текстовая причина сохраняется.
- Новый профиль, выполненное условие покупки и уже купленный герой различаются.
  Выполненное условие ещё не разрешает старт до покупки; покупка остаётся только
  в существующем Meta, без нового перехода Character Select → Meta.
- Tab/Shift+Tab перемещают фокус; Enter/Space активируют текущий control. Escape —
  Back на этих двух экранах, без global pause. Двойной click/submit не создаёт
  два перехода/run. Footer не находится под карточками и не сдвигается от выбора.
- Пустой/недоступный runtime roster: не подставлять fixture/locked hero; показать
  диагностируемую ошибку загрузки, сохранить Back, отключить confirm. Отсутствующий
  production sprite — ошибка binding, не повод выдумать новый арт.

## Контент и границы макета

Полностью прочитаны CHAR-001/002, FIELD-001…010 и SKILL-001/003 из CD;
учтены UI §§2–5 и DECISION-0026/0050/0081/0083/0086. Допустимые production пути
проверены через FixtureSprites и существующие catalogs. Значения из макета не
являются новым authoring source: авторитеты — CD и связанные inputs генератора.

На момент исходного HTML в ProductionCharacters была только CHAR-001. После
интеграции соседней ветки каталог содержит десять героев; Unity entry R1 читает
его фактический состав. Сам HTML не служит доказательством runtime binding.
FIELD-001…003 — текущие production definitions;
FIELD-004…010 показаны по approved CD/thumbnail, без production wiring. Игровые
приёмки полей/каталогов этим макетом не закрываются. Profile presets постановочные:
«Новый», «Пройдена окраина», «Бугор куплен». Ни покупки, ни сохранение не выполняются.

Стресс 10 героев / 15 полей повторяет существующие изображения и помечает дополнительные
записи «Тестовая карточка». Он проверяет вместимость, не показывает ложный готовый
roster. Settings, Meta, Exit и Start в HTML дают только сообщение о намерении.
Баланс, input preference, runtime code, JSON, production PNG и `.meta` не меняются.
Пять новых preview PNG главного меню находятся только в ignored TestResults.

## Перенос после утверждения

1. Зафиксировать выбранную композицию/inspection UX в UI §§3–5 и decision;
   синхронизировать IP-12/IP-16/IP-26 contracts без изменений gameplay access.
   Если выбран D или E, отдельно подготовить одобренный art packet с точным hash и
   approval evidence через art_pipeline.py; затем import и scoped art checks.
2. Переиспользовать AppShellScreen/Presenter, CharacterSelectScreen/Presenter и
   FieldSelectScreen/Presenter; отдельно хранить read-only inspection и допустимый
   подтверждённый selection. Добавить typed данные вместо парсинга summary strings.
3. Изолировать USS по экрану; не перекрашивать принятые HUD/Draft/Pause или Meta
   общими selectors. Flex layout, стабильные semantic IDs, старые model intents.
4. Проверить оба размера в Unity, условия покупки/lock, keyboard focus, Back,
   no-double-start, profile/read failures и запуск с выбранными character/field.
   Перед Unity tests — smoke-check. HTML evidence не заменяет runtime проверки.

Для approval сейчас: общая композиция трёх экранов, крупный герой/thumbnail,
короткая информация, просмотр закрытых вариантов без выбора, раздельные confirm.
Results/Meta/Settings и расширение каталогов в этот шаг не входят.
