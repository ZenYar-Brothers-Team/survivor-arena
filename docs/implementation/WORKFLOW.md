# Implementation Plan → Code

Этот файл — обязательный контракт работы coding AI. Он применяется как при реализации явно указанного IP, так и при запросе «реализуй следующую часть».

## 1. Выбор модуля

Если пользователь указал IP, выбрать его. Иначе открыть [`STATUS.md`](STATUS.md) и выбрать первый по номеру модуль со статусом `Ready`.

До изменения кода проверить:

- все зависимости имеют статус `Implemented` или `Verified`;
- production-модуль не заблокирован Draft-сущностью или другим content gate;
- в репозитории нет более новой реализации, не отражённой в статусе;
- scope модуля не конфликтует с явной командой пользователя.

Если репозиторий и `STATUS.md` расходятся, сначала провести read-only аудит и исправить статус/evidence. Не повторять уже реализованную работу.

## 2. Implementation packet

Перед реализацией прочитать:

1. этот workflow;
2. запись выбранного IP в [`STATUS.md`](STATUS.md);
3. спецификацию IP в [`modules/`](modules/);
4. только перечисленные в Context секции Game Design;
5. только перечисленные секции или полные карточки ID Content Design;
6. релевантный код, тесты и локальные repository instructions.

Если IP ссылается на content ID, читать полную карточку ID и только явно связанные карточки, необходимые для scope. Весь Content Design читать не требуется.

## 3. Source of truth

- Game Design — общие игровые правила и взаимодействия систем.
- Content Design — конкретные сущности, behavior и balance-data.
- IP specification — scope, зависимости, acceptance criteria, проверки и out of scope.
- Repository/code — фактически реализованная архитектура и ограничения.
- `STATUS.md` — только состояние исполнения и evidence.

IP не переопределяет дизайн. Код не превращается в новый дизайн только потому, что уже написан.

## 4. Статусы и начало работы

Допустимые статусы:

- `Ready` — зависимости и gates выполнены, работу можно начинать;
- `In progress` — модуль сейчас реализуется;
- `Implemented` — acceptance criteria реализованы, но полная проверка ещё не подтверждена;
- `Verified` — проверки успешно выполнены и evidence записан;
- `Blocked` — существует конкретная dependency, content gate или design decision;
- `Superseded` — модуль заменён другим утверждённым scope.

Перед существенными изменениями перевести выбранный модуль в `In progress`. Не менять статус спецификации модуля: он хранится только в `STATUS.md`.

## 5. Правила реализации

- Реализовывать только Scope и необходимые технические предпосылки.
- Не включать Out of scope «заодно» без явной необходимости или команды пользователя.
- Не зашивать TBD-значения как необратимые правила; использовать config или явно названные fixtures/placeholders.
- Fixture не должен копировать Draft-значения так, будто они Approved.
- Сохранять стабильные content ID и валидировать ссылки между definitions.
- Добавлять автоматические тесты там, где acceptance criteria можно проверить без ненадёжной визуальной оценки.
- При невозможности автоматизации записывать воспроизводимый manual check.

## 6. Content gate и Design Gap

Draft-сущности можно использовать в framework-модулях только как non-binding compatibility targets. Production-реализация конкретного Draft ID запрещена без явного approval пользователя.

Если конкретная сущность требует отсутствующей общей механики, это Design Gap. Coding AI не изобретает правило внутри сущности и не расширяет GDD молча. Нужно описать gap, определить затронутые IP/ID и запросить продуктово значимое решение.

## 7. Обратная синхронизация

После реализации классифицировать каждое отклонение:

- локальная техническая деталь без изменения контрактов — design docs не меняются;
- изменение scope, зависимости, acceptance criteria или ownership — обновляется IP specification;
- изменение behavior/параметров конкретной сущности — обновляется Content Design;
- изменение общего игрового правила — обновляется Game Design и проверяется влияние на остальные IP;
- межслойное или спорное решение — создаётся запись в [`../decisions/`](../decisions/) и до approval не считается каноном.

Если изменение Game/Content Design не было явно разрешено и меняет продуктовый смысл, coding AI сначала предлагает изменение. Исправление очевидной рассинхронизации, ссылок или evidence можно выполнять вместе с кодом.

## 8. Завершение модуля

Перед завершением:

1. проверить каждое acceptance criterion;
2. выполнить перечисленные checks в разумном для риска объёме;
3. проверить regressions в затронутых системах;
4. обновить `STATUS.md`: status, implementation evidence, verification evidence, deviations, documentation impact;
5. обновить готовность зависимых модулей;
6. синхронизировать затронутые design-документы или явно записать `Documentation impact: none`;
7. убедиться, что новые ссылки и content IDs валидны.

`Verified` разрешён только после успешной проверки. Наличие тестового файла без запуска означает максимум `Implemented`.

## 9. Отчёт пользователю

Финальный отчёт должен кратко содержать:

- реализованный IP и результат;
- основные изменённые файлы;
- выполненные проверки и их результат;
- новый статус модуля и следующий `Ready` IP;
- зафиксированные отклонения, gates или решения пользователя.
