# Implementation Plan → Code

Этот файл — обязательный контракт работы coding AI. Он применяется как при реализации явно указанного IP, так и при запросе «реализуй следующую часть».

## 1. Выбор модуля

Если пользователь указал IP, выбрать его и проверить зависимости/gates. Иначе открыть [`STATUS.md`](STATUS.md), прочитать Execution order и выбрать первый в этой очереди модуль со статусом `Ready`. Номер IP — стабильный ID, а не позиция очереди. Пропускать завершённые и Blocked; невыполненный prerequisite нельзя обходить ради позиции в очереди. Если Ready нет, назвать конкретные blockers и следующий reviewable packet, не возвращаться к устаревшему scope.

До изменения кода проверить:

- все зависимости имеют статус `Implemented` или `Verified` для требуемой целевой ревизии scope; historical evidence прежнего scope не заменяет эту проверку;
- выбранный production packet имеет approved design и полные используемые данные/ассеты; approval 121 карточки по DECISION-0015 уже получен, но реальные оставшиеся Draft/TBD и content gates не снимаются автоматически;
- в репозитории нет более новой реализации, не отражённой в статусе;
- scope модуля не конфликтует с явной командой пользователя.

Если репозиторий и `STATUS.md` расходятся, сначала провести read-only аудит и исправить статус/evidence. Не повторять уже реализованную работу.

## 2. Implementation packet

Перед реализацией прочитать:

1. этот workflow;
2. запись выбранного IP в [`STATUS.md`](STATUS.md);
3. спецификацию IP в [`modules/`](modules/);
4. только перечисленные в Context секции Game Design;
5. только перечисленные секции или полные карточки ID Content Design, релевантные секции UI/UX, Art Direction/Art Production и Asset Pipeline;
6. релевантный код, тесты и локальные repository instructions.

Если IP ссылается на content ID, читать полную карточку ID и только явно связанные карточки, необходимые для scope. Весь Content Design читать не требуется.

Собирать контекст по необходимости:

- Из STATUS сначала прочитать шапку с pause/stop boundaries, Execution order и найти строки `Status:`; затем полную запись выбранного IP и нужных dependencies. Историю проверок для выбора следующего IP не читать.
- Перед чтением большого файла искать `rg -n` по заголовку, ID или символу и читать полный нужный раздел/тип. Расширять чтение по найденным зависимостям и неясностям, а не выгружать целые каталоги.
- Уже прочитанный и неизменившийся текст в той же задаче повторно не загружать. После смены задачи или compaction восстановить недостающие факты из файлов; память не заменяет актуальный статус.
- Подробное evidence читать по ссылке выбранного IP только для проверки реализации, покрытия или расхождения. Архив старого scope не является текущим approval/gate.
- Применимые правила выбирать по таблице в корневом `AGENTS.md`; helpers — по `.claude/README.md`. Не читать все skills, proposals, decisions и архивы при старте каждого IP.
- Независимые поиски объединять в один вызов; возвращать нужные фрагменты и краткие результаты. Если вывод обрезан, сузить запрос и дочитать недостающее перед выводами.

## 3. Source of truth

- Game Design — общие игровые правила и взаимодействия систем.
- Content Design — конкретные сущности, behavior и balance-data.
- UI/UX Design — экраны, состояния и взаимодействия; Art Direction/Art Production — визуальное направление и inventory; Asset Pipeline — техническая подготовка/импорт/approval изображений.
- IP specification — scope, зависимости, acceptance criteria, проверки и out of scope.
- Repository/code — фактически реализованная архитектура и ограничения.
- `STATUS.md` — состояние исполнения, краткое evidence и ссылки на подробные записи в `evidence/`; только STATUS определяет текущую применимость этих записей.

IP не переопределяет дизайн. Код не превращается в новый дизайн только потому, что уже написан.

## 4. Статусы и начало работы

Допустимые статусы:

- `Ready` — зависимости и gates выполнены, работу можно начинать;
- `In progress` — модуль сейчас реализуется;
- `Implemented` — acceptance criteria реализованы, но полная проверка ещё не подтверждена;
- `Verified` — проверки успешно выполнены и evidence записан;
- `Blocked` — существует конкретная dependency, content gate или design decision;
- `Superseded` — модуль заменён другим утверждённым scope.

Перед существенными изменениями перевести выбранный модуль в `In progress`. Не менять статус спецификации модуля: он хранится только в `STATUS.md`.

### Scope revision и catalog packets

STATUS хранит Scope revision (общую в шапке, исключения в записи IP), текущий packet, оставшиеся acceptance/IDs, краткое target implementation/verification evidence и ссылки на подробности. Поля, одинаковые для ещё не начатых IP, определены один раз перед записями; отклонения указывать явно. Подробные датированные записи — в `evidence/`, historical evidence отделено от target. Module/evidence files не содержат текущего status. Для текущего плана ревизия — `design-sync-R2`.

Без behavioral delta IP-00/IP-02 сохраняют проверенное состояние после проверки совместимости. Для изменённого scope прежнее Verified остаётся историческим; новые критерии проходят Ready/Blocked → In progress → Implemented → Verified по фактической работе.

Каталог может поставляться конкретными согласованными наборами ID с полными данными. Ready означает, что текущий packet подготовлен и prerequisites/gates выполнены; после старта — In progress. Выполненный поднабор фиксируется checklist в STATUS, но весь IP не становится Implemented/Verified до закрытия всего обязательного scope. Если продолжить ни один оставшийся packet нельзя — Blocked с конкретной причиной. Новые статусы вроде Partially Verified не вводятся.

При изменении dependency/API/acceptance пересчитать готовность потребителей; не переносить прежний Next Ready вручную. Execution order хранится только в STATUS. Изменение очереди требует согласованного обновления плана; изменение номера файла для этого не нужно.

## 5. Правила реализации

- Реализовывать только Scope и необходимые технические предпосылки.
- Не включать Out of scope «заодно» без явной необходимости или команды пользователя.
- Не зашивать TBD-значения как необратимые правила; использовать config или явно названные fixtures/placeholders.
- Fixture не должен копировать Draft-значения так, будто они Approved.
- Сохранять стабильные content ID и валидировать ссылки между definitions.
- Добавлять автоматические тесты там, где acceptance criteria можно проверить без ненадёжной визуальной оценки.
- При невозможности автоматизации записывать воспроизводимый manual check.

## 6. Content gate и Design Gap

Draft-сущности можно использовать в framework-модулях только как non-binding compatibility targets. Production-реализация конкретного Draft ID запрещена без явного approval пользователя.

Если конкретная сущность требует отсутствующей общей механики, это Design Gap. Coding AI не изобретает правило внутри сущности и не расширяет GDD молча. Нужно описать gap, определить затронутые IP/ID и запросить продуктово значимое решение.

## 7. Обратная синхронизация

После реализации классифицировать каждое отклонение:

- локальная техническая деталь без изменения контрактов — design docs не меняются;
- изменение scope, зависимости, acceptance criteria или ownership — обновляется IP specification;
- изменение behavior/параметров конкретной сущности — обновляется Content Design;
- изменение общего игрового правила — обновляется Game Design и проверяется влияние на остальные IP;
- межслойное или спорное решение — создаётся запись в [`../decisions/`](../decisions/) и до approval не считается каноном.

Если изменение Game/Content Design не было явно разрешено и меняет продуктовый смысл, coding AI сначала предлагает изменение. Исправление очевидной рассинхронизации, ссылок или evidence можно выполнять вместе с кодом.

## 8. Vertical UI / observability

Каждый IP обязан явно описать свой `UI / observability` контракт. Если модуль вводит состояние или действие, видимое игроку, тот же IP расширяет immutable ViewState, presenter intent, UXML/USS с semantic element IDs, fixture-состояния и PlayMode smoke. Скрытый infrastructure-модуль вместо production UI предоставляет достаточную debug/test observability и явно фиксирует, что отдельный player-facing surface не нужен. UI не владеет gameplay state. IP-26 объединяет и завершает уже поставленные vertical slices, а не откладывает их первое появление.

Для любой development/debug поверхности обязателен полный контракт в [ui-code.md](../../.claude/rules/ui-code.md): development gating, collapsed launcher, bounded tabs/scroll и View/presenter/model boundary.

## 9. Завершение модуля

Перед завершением:

1. проверить каждое acceptance criterion;
2. выполнить перечисленные checks в разумном для риска объёме;
3. проверить regressions в затронутых системах;
4. обновить `STATUS.md`: status, implementation evidence, verification evidence, deviations, documentation impact;
5. обновить готовность зависимых модулей;
6. синхронизировать затронутые design-документы или явно записать `Documentation impact: none`;
7. убедиться, что новые ссылки и content IDs валидны.

`Verified` разрешён только после успешной проверки. Наличие тестового файла без запуска означает максимум `Implemented`.

Порядок проверок без лишних повторов:

- До запуска составить краткий набор checks из acceptance criteria, изменённых контрактов и риска регрессий. Использовать существующие тесты, добавлять проверки нового поведения/исправляемой ошибки.
- Во время правок запускать затронутые тесты. После стабилизации выполнить весь обязательный набор IP, включая полный EditMode/PlayMode прогон, когда он требуется. Экономия не отменяет обязательную проверку.
- Успешный прогон применим к проверенной версии кода/config/assets. Повтор нужен после влияющих на него изменений, сбоя или новой конкретной неопределённости; одна редактура текста не требует повторного Unity run.
- Перед **каждым** запуском соблюдать [smoke-check](../../.claude/skills/smoke-check/SKILL.md): свежая проверка Editor, безопасный способ запуска. Это ограничение не ослабляется ради экономии.
- В контекст возвращать дату, Unity version, scope/filter, passed/failed/skipped и ошибки с нужным окружением. Полные логи/результаты оставлять файлами; прочитать детали сбоя перед исправлением.
- В STATUS держать краткий итог и ссылку на датированное `evidence/<revision>-<date>.md#ip-nn` с деталями реализации, coverage, условиями и путями результатов. Историю не дописывать в каждую запись STATUS. Для чисто документационной правки достаточно релевантных проверок ссылок/структуры/согласованности, если она не меняет исполняемые артефакты.

При обработке пользовательского плейтеста сохранять отзыв и выбранный report в [docs/playtests](../playtests/README.md). Ссылка на файл + OBS-NN связывает исходную цитату, диагностику, исправление и повторную проверку. Успех telemetry checks не закрывает gameplay-замечания автоматически.

## 10. Отчёт пользователю

Финальный отчёт должен кратко содержать:

- реализованный IP и результат;
- основные изменённые файлы;
- выполненные проверки и их результат;
- новый статус модуля и следующий `Ready` IP;
- зафиксированные отклонения, gates или решения пользователя.

## 11. Размер задачи и модель

- Для нового IP после завершённого и закоммиченного модуля предпочтительна отдельная задача с небольшим стартовым контекстом. Создавать её только по явному запросу пользователя. Незавершённый IP продолжать в своей задаче; указание пройти несколько IP подряд и заданные stop boundaries имеют приоритет.
- Для передачи достаточно ссылки на STATUS и спецификацию, текущей ветки/commit и незакоммиченных изменений, проверок и нерешённых вопросов. Не копировать историю диалога и design bodies; не создавать второй реестр статусов.
- Рабочая рекомендация по модели: Astra + Medium для сложного IP с ясным scope; Astra + High для архитектурной неопределённости или трудной диагностики; Terra + Medium для небольших локальных правок; Low для рутинной операции вроде commit. Более высокий effort использовать по конкретной необходимости. Это рекомендация, не автоматическая смена выбранной пользователем модели/effort.
- Оценивать экономию по завершённой работе с учётом повторных исправлений; меньшая модель не гарантирует меньший суммарный расход. Не запускать дополнительные agents или все review skills по умолчанию.
- Подключать инструменты/skills по задаче. Не отключать и не удалять глобальные плагины пользователя ради локальной оптимизации контекста.
